## Construction and provenance

[capture.py](capture.py) adapts the existing inventory Host / whole-lookup pattern but runs the complete immutable source with only its `bitgn` transport replaced. It never sets or injects `WORLD`. The real agent performs bootstrap Tree/Read/Exec calls, reads the routed catalogue policy, runs its own catalogue Tree/Read index builder, and creates the post-catalogue LLM request.

The Host supplies archived security/availability policies, identity, and clock from the existing record-t091 fixture. AGENTS receives exactly one synthetic adaptation: its catalogue source root changes from `/proc/products` to `/proc/catalog` to agree with the synthetic product paths and catalogue lookup policy. The complete original AGENTS response, exact replacement, and before/after content hashes are preserved in scaffolding provenance; all other policy clauses are unchanged. The catalogue lookup policy comes from the archived parent request in the earlier paired diagnostic. Product files and instructions are synthetic. Directory listings/recursive Tree responses are reconstructed deterministically from those files with depth semantics from `proto/bitgn/vm/ecom/ecom.proto`: root depth is zero, positive levels cut descendants at that depth, and level zero recurses fully. Cut directories omit `children`, matching archived Tree response 12117. They are simulated rather than live service responses. [scaffolding-provenance.json](scaffolding-provenance.json) identifies source event numbers and the source message; [DEPENDENCIES.json](DEPENDENCIES.json) pins all source files.

The scripted router selects `/docs/catalogue-lookup.md`; the first scripted main-loop response is each fixture's declared catalogue action. The next main-loop request is captured intact; a final inert clarification stub then closes the agent run. Scripted responses are not evidence that a real router or model would select those actions. Host rejects unexpected/mutating RPCs. Catalogue files are actually read through the source index path, rather than injected into an already-built index.

**U4 glossary is now actual shared context.** Only U4 appends its exact glossary to `/docs/catalogue-lookup.md`. The agent actually issues the Read; both full C/L message histories contain that same policy observation exactly once. No manually authored semantic relation/oracle labels are passed to the agent.

The initial Host ignored `level` and therefore leaked nested SKU filenames into the root bootstrap; that unsubmitted capture was corrected. [tree-depth-evidence.json](tree-depth-evidence.json) records the contract, archived response shapes, and independent per-fixture depth checks at levels 1–4 and 0. Archived RPC files contain responses only; request arguments are verified from source, not claimed to be in the archive. Every regenerated actual root-level-2 prompt is asserted to stop at `/proc/catalog`, with no product descendants, while the source `/proc` level-0 index still reads every supplied product file. All 68 source/runtime captures were regenerated after both corrections.

## Exact request isolation

Each file in [requests](requests) contains the captured source-level SDK call (positional arguments and keyword settings), a normalized complete `C` request, the derived `L` request, and a reversible removed-field ledger. C includes all messages plus `model`, `max_completion_tokens`, `reasoning`, and `temperature`. This is the actual SDK input generated by source; no private HTTP/provider transformation is claimed or guessed.

L is derived only after the actual bounded observation has been generated: delete the two lexical found/absent fields from already-selected sibling rows. All other messages and settings, original matches/order/scores, product facts, counts, and truncation flags remain identical. Reinserting precisely those fields restores the full C request, including the original observation text. The U4 policy/glossary message is unchanged between arms.

All four source/runtime executions produce identical RPC traces, scripted answers, and captured SDK requests per fixture. Native Monty runs use **10-second feed/turn limits and 1,000 suspensions**, not the looser older harness settings. [host-traces.json](host-traces.json) preserves the actual calls and captures; [worlds.json](worlds.json) preserves all supplied file bodies and reconstructed listings. [results.json](results.json) pins the outputs and records per-execution timings, actual evidence metadata, and request byte sizes.

## Finding from real indexing

The F2 fixture illustrates why the complete runtime path matters. The real directory traversal groups brand records; with the scripted top-two query, both original matches come from the first family. The agent indexes all **32 products**, but the sibling attachment has **16 eligible records**, of which **10 are shown**. The earlier prebuilt-index matrix interleaved families and had 32 eligible siblings. We do not claim equality to that artificial ordering. The C/L comparison remains isolated within the actual runtime request, and supporting P-N15 remains hidden by truncation.

Byte accounting is not token or price estimation: the 17 C requests total **251,507 compact UTF-8 JSON bytes**, and L totals **245,009**. Individual C requests range from 13,824 to 20,982 bytes. No tokenizer was invoked, no paid inference occurred, and no future dollar estimate is inferred from byte counts. Actual scripted SDK invocation counts are kept separate from real model calls (zero).

## Reproduce and limits

From the repository root:

```sh
UV_CACHE_DIR=/tmp/ecom1-uv-cache uv run --python 3.14 --no-project --offline --with pydantic-monty==1.2.0 python research/ecom1/2026-10-22-sku-lexical-runtime-prompts/capture.py
```

This regenerates files only in this directory. Source and fixture hashes are enforced. Timings can vary; deterministic request hashes should remain identical on the pinned inputs/runtime. The legacy source contains an existing invalid-escape SyntaxWarning during parsing; it was not edited.

The 68 executions demonstrate source/runtime and prompt-construction parity on the scripted path. They do not establish model compliance, live provider wire-format equality, catalogue completeness beyond supplied synthetic files, future action safety, semantic-score gain, or full100 readiness. No paid test should be dispatched automatically. Independently review complete prompt parity and shared context, then separately choose any future bounded semantic assessment.
