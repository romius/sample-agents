## What our lineage does and does not add

`source-comparison.json` pins both readable sources and lists 112 identical shared function definitions, ten changed shared functions and both sets of unique functions. Initialization/dispatch order is deliberately not inferred from function equality.

- **C/L SKU evidence:** both actual t027 count and t062 stock instructions are outside `sku_lookup_description` scope. A syntactically supported SKU-only `outside...` request is accepted verbatim, but neither the scope helper nor lexical found/absent metadata solves negation. The count early answer bypasses model-only observations. The prepared C/L diagnostic measures a different uncertainty and cannot establish a fix for either zero.
- **Crosslist:** our d5789 parser is AST-identical to the winning parser and rejects the same OCR. Our original-first quantity fallback is a **receipt parser** change, not a crosslist repair. The archived old bobcat crosslist parser succeeds here; future exploration should retain the winning parser first, use only tightly evidenced layout normalization on decline, then revalidate unique branch, both totals, row sequence, exact properties and normalized output. Current tests reject duplicate plain totals and inconsistent totals; a prose-embedded total remains ignored by the existing anchors. A general substring search or broad prefix stripping would weaken those boundaries. No new normalizer is implemented in this audit.
- **Receipts:** all five recorded receipt tasks score1. STACK E already includes bobcat receipt v2 plus inherited receipt reference logic. Our receipt quantity/header/price changes therefore have no demonstrated score headroom in this run and require their fresh malformed/price-conflict oracles before any port. Avoid replacing the successful handler wholesale.
- **Inventory:** our validated compiler/collector provides stronger preparation, revalidation, one-write/readback and terminal post-write uncertainty handling, but is much larger than a surgical reference repair. First establish the grader-reference cause with reproducible archived/runtime evidence. If the stronger compiler is integrated, replace the overlapping active `i2c_csv_export` route and use the verified named SDK callback wrapper; do not append a competing handler or revert to the weaker parent. New date/store/family fixtures and post-write fault cases remain necessary.
- **Exec404/retry:** parent separately reproduced the exact-source guard matrix in `../2026-10-23-stack-e-integration-plan/compare_guards.py` and `guard-comparison.json`. The winning source already handles missing executables generically; the narrow donor distinguishes that from payment-not-found. Blindly adding max3 MSR inside the existing max3 broad main-loop catch creates nine attempts; outer catches also retry permanent errors/cancellation. This requires replacement of overlapping retry ownership, not a global four-callsite text substitution. Actual t076 timeout is downstream of the OCR/length failures; another attempt alone is not evidence it fixes the task.
- **Cleanup/Delete:** the active exact STACK E `i2c_cleanup` reproduces the prior partial-Delete counterexample in both CPython and native ClassInstance. Two files are requested, a.txt succeeds, b.txt raises404 and remains; handler returns OUTCOME_OK for only a.txt. The success control deletes both and returns both; a directory entry correctly declines before Delete. All observed cleanup-related grades are already1, so this is a reachable host-failure correctness risk, not measured score gain. Preserve the successful lane: track confirmed vs unconfirmed effects, do not retry uncertain Delete, inspect actual remaining entries, and terminate honestly without fallthrough that repeats mutations. Blanket disabling the whole handler would discard proven coverage.
